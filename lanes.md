(iii) a registrar / factory table switches a class to autowiring only when no test relies on the hand-built path; otherwise the entry passes the one new aggregate; every T lane may edit the table entries for classes it owns (same rule for BuiltinIntegrationServices.php and MagicMapper's hand-built Magic*Handlers). (iv) Rule 5 only protects other apps: no external caller → migrate in-repo callers and delete the old signature; external caller → ≤5-line delegate, named app+file. (viii) 3–4 param constructors of "domain collaborator + Logger/guard" with no honest 3-consumer aggregate are LEFT (e), no one-class aggregates. ## Sizing: constructors with 3 and 4 parameters (LEFT (e))

| | units | LOC | of it with LoggerInterface |
|---|---|---|---|
| 3-param ctors (all kinds) | 1,071 | 7,301 | 265 / 1,805 |

| controllers | 297 | 2,383 | |

If every 3–4 param constructor dropped out, > 2 would fall from 17.16% to 12.22% (−4.9 points); only the all-DI ones: to 14.14% (−3.0); only the autowired non-controller ones: −1.9 points; only those with a Logger: −1.1 points.

Options, judged on design rather than metric:
- **(a) keep as residue.** Honest: a class with a domain collaborator, a guard and a logger has three real dependencies. Costs ~1.9 points of > 2 that will never come back.
- **(b) shared capability aggregates per area**, reused by 3+ classes (the existing SchemaCatalog / ControllerServices pattern). The data supports it where collaborators genuinely recur: Register+Schema mapper pairs (with or without ObjectOperations / MagicMapper) recur in dozens of classes, IGroupManager+IUserManager+IUserSession and AuditTrailMapper+IUserSession recur. Good design where the trio is a real capability ("schema lookup", "who is acting"); gaming where it bundles unrelated services to hit 2.
- **(c) the logger is not a collaborator to pass**: use Nextcloud's container-provided LoggerInterface through a narrow per-area aggregate only where the area already has one; not a static/global logger (hidden dependency, worse testability).

**Recommendation: (b), restricted.** Allow an aggregate only when it names a capability and has at least 3 consuming classes in the same area (existing Rule 4 bar), and let LoggerInterface ride in an existing aggregate of that area rather than create logger-only aggregates. Everything else stays residue (a). Expected yield: roughly a third of the 6,277 autowired LOC (≈ 2,000 LOC, ~0.6 points), which is enough together with wave U and does not trade design for the number.
