## 3. Opt-in `searchable` property flag

- [x] 3.1 Extend the schema-property iteration loop in `MagicMapper::createTableForRegisterSchema()` (the same loop that already checks `facetable`) to also check `$propertyConfig['searchable'] ?? false`, creating `CREATE INDEX IF NOT EXISTS {table}_{col}_trgm_idx ON {table} USING GIN ({col} gin_trgm_ops)` when true, Postgres + `hasPgTrgmExtension()` gated, wrapped in the same try/catch-and-skip pattern as the neighbouring `facetable`/relation index creation. — added directly after the `facetable` btree branch in `createTableIndexes()`; a failed index attempt logs a warning and continues.
- [x] 3.2 Confirm whether `MagicTableHandler::syncTableForRegisterSchema()`'s existing-table update path already re-invokes the facetable/relation/baseline-`_name` index-creation routine; wire the retrofit call so both the baseline `_name` index and newly-`searchable`-flagged properties get indexed on an existing table when the schema changes (see design.md Decision 4 / Open Questions). — **CONFIRMED: no new call needed.** `syncTableForRegisterSchema()` (`MagicTableHandler.php:473`) already calls `MagicMapper::updateTableIndexes()`, a thin wrapper that re-runs `createTableIndexes()` in full on every sync. Since both index kinds use `CREATE INDEX IF NOT EXISTS`, they retrofit idempotently onto existing tables the moment the schema is synced (or `pg_trgm` becomes available). This resolves the design.md Decision 4 Open Question in favour of "the existing routine is re-invoked" — covered by test 5.3.
