# U03: references kept in `lib/Service/Aggregation` (Core to Search) and `lib/Service/FileService.php` (Core to Files)

Package U03 (wave 4). Measured with the modularity ratchet (`modularity_check.py`) on `origin/main` 6655f596 (179 references
against the order). All 12 references of the package were still there, and all 12 are kept. Each row below
says what was tried, what it would break, and what lets the reference go later.

The simulations reassign csv rows in `scripts/component-map.csv`, regenerate the generated component patterns
and deptrac area layers from it, and run `modularity_check.py --check`. The csv is restored afterwards.

## Aggregation: Core to Search (6)

Two clusters share one cause. The runner's own API (`run`, `runAdhoc`, `runAdhocByRef`) and its result cache
are built on Search's aggregation value objects. `AggregationQuery` is used by other apps by name (22 fleet
references), so it cannot move, be renamed or be copied into Kernel. A Core port for the runner would have
to name it in its signature. The Search design (`contracts/search.md`, A4 and A5) decided that the aggregation
engine is Search's work: its csv rows, together with `lib/Service/GraphQL`, count to Search. That is the
allowed move (3). It cannot land yet, for the reasons in the table under the rows.

| Source | Target | Why no allowed move fits now | What lets it go |
|---|---|---|---|
| `lib/Service/Aggregation/AdhocAggregationRun.php` | `lib/Search/Service/Aggregation/AggregationQuery.php` | The run's parameter object carries the query the caller built. A Core port or Kernel copy of `AggregationQuery` would copy the class, and the class cannot move (fleet). Counting the file to Search: see the measurements below. | The rows of A4 and A5. |
| `lib/Service/Aggregation/AggregationRunner.php` | `lib/Search/Service/Aggregation/AggregationQuery.php` | The runner executes the query object it receives (`runAdhoc(RegisterSchemaRef, AggregationQuery)`, a public method that buildiq, pipelinq and shillinq call). Same as above. | The rows of A4 and A5. |
| `lib/Service/Aggregation/AggregationRunner.php` | `lib/Search/Service/Aggregation/AggregationCacheInterface.php` | The runner reads and writes its 60-second cache (`get`, `set`, `getAdhoc`, `setAdhoc`). The adhoc methods take `AggregationQuery` and the named ones take `AggregationSlot`, so a Core port would name the same Search types. Moving the caching out of the runner (an event that returns a cached result) changes the hit and miss path, so behaviour would not stay identical. | The rows of A4 and A5. Cache and runner are then one area. |
| `lib/Service/Aggregation/AggregationRunner.php` | `lib/Search/Service/Aggregation/AggregationSlot.php` | The cache key of a named aggregation. Only the cache and the runner use it. It is part of the cache API above. | The rows of A4 and A5. |
| `lib/Service/Aggregation/AggregationRunner.php` | `lib/Search/Service/Aggregation/CrossSchemaTarget.php` | It reads a declared spec's `schema` key so the validator (Search) and the runner read a spec the same way. Counting it to Core would only hide the reference: in the decided end state both of its users are Search. | The rows of A4 and A5. |
| `lib/Service/Aggregation/AggregationRunnerInterface.php` | `lib/Search/Service/Aggregation/AggregationQuery.php` | The runner's interface declares `runAdhoc(..., AggregationQuery $query)`. Same as above. | The rows of A4 and A5. |

What the row move does on 6655f596:

| Rows counted to Search | Gone | New against the order | Newly exposed Core files |
|---|---|---|---|
| Only `AggregationRunner`, `AggregationRunnerInterface`, `AdhocAggregationRun` | 4 | 1 (`Service/GraphQL/ListAggregations` to `AggregationRunner`) | 24 (the runner's own helpers in `lib/Service/Aggregation` and Core internals) |
| All of `lib/Service/Aggregation` (A5 alone) | 6 | 5: `ListAggregations` to `AggregationRunner`, `NamedAggregationOptions`, `NamedAggregationRef`; `Service/Schemas/SchemaDeclarationValidators` to `WidgetAnnotationValidator` and `WidgetAnnotationValidatorInterface` | 9 |
| `lib/Service/Aggregation` and `lib/Service/GraphQL` (A4 and A5) | 8 | 2 (the two `SchemaDeclarationValidators` references) | 15 |

A PR that adds a reference against the order is refused, and newly exposed files are allowed only as a
deliberate contract. The 15 Core files are not contracts: `OrganisationScopeResolverInterface`,
`OrganisationlessAdmission`, `DraftListLens`, `DraftListing`, `PreservedListLens`, `PreservedListing`,
`TranslationScope`, `DbalObjectSourceProvider`, `AggregateVisibility` (from the runner), and `GetObject`,
`ObjectFindRequest`, `ReadScope`, `RelationHandler`, `RelationLookup`, `PropertyWriteCheck` (from the GraphQL
resolver). `ListAggregations` is package U06's file, so U03 could not change it.

Three changes let all six references go, in this order:

1. **The widget annotation check is contributed through `SchemaDeclarationChecksEvent`**, in the slot where
   `RecordAnnotationRefusals` runs it today, as Compliance, Integrations and Search's unique-hint check do
   (#10685). Then `SchemaDeclarationValidators::widgets()` no longer names the validator. This adds a listener,
   so `listener-order.json` and `ListenerRegistrationOrderGoldenTest` change.
2. **Core contracts for what the engine reads from the object store** (the Core design's D02 set): an object
   read through the Kernel `ObjectOperationsInterface`, a relation lookup port, aggregate visibility, the
   draft and preserved list lenses, the organisation scope and the DBAL object source. The runner and the
   GraphQL resolver then type those contracts instead of the 15 classes.
3. **The rows of A4 and A5 in one PR.** Measured: 8 references gone, none new.

## FileService: Core to Files (6)

`FileService` is the facade of the file store. It implements the Files interfaces `FileServiceInterface` and
`FileHandlerSupportInterface`, delegates to the Files ownership, sharing and audit handlers, and returns the
Files metadata entity. That is Files' work. The decided move is the Files design's B6
(`contracts/files.md`, A1): `lib/Service/File/*` (except the seven Core vocabulary and upload-rule files in A2)
and `FileService` count to Files together, once Core reaches them only through Core ports (B3, B4). None of
these references can be removed inside `FileService` itself: each one is the facade doing its own work.

| Source | Target | Why no allowed move fits now | What lets it go |
|---|---|---|---|
| `lib/Service/FileService.php` | `lib/Service/FileServiceInterface.php` | `FileService` implements it, and Files' controllers (`FilesController`, `FileStore`, `FileTextDomain`, `ObjectFolderBrowser`, `FileMetadataFormHandler`) depend on it. Counting the interface to Core would only hide the reference and make those Files callers depend on a Core copy of Files' own API. | B6. |
| `lib/Service/FileService.php` | `lib/Service/FileHandlerSupportInterface.php` | `FileService` implements it for its own handlers (`setFileService()`). The handlers are packages U01 and U02. Counting the interface to Core would also only hide the reference. | B6. |
| `lib/Service/FileService.php` | `lib/Files/Db/File.php` | `changeFileMetadata(): Files\Db\File` is a public method that 10 fleet apps can call (54 files use `FileService`). `FileServiceInterface` declares the same return type. Changing it to a Kernel value narrows what callers get back, which breaks them. | B6. |
| `lib/Service/FileService.php` | `lib/Files/Service/File/FileOwnershipHandlerInterface.php` | `getUser()` and `getCurrentUser()` fit the Core port `FileAccountInterface`, but `transferFolderOwnershipIfNeeded($folder, $sharingHandler)` passes the Files sharing handler so the folder is shared back. A Core port for that would name the Files sharing handler or copy the ownership interface. | B6. |
| `lib/Service/FileService.php` | `lib/Files/Service/File/FileSharingHandlerInterface.php` | `findShares()` and `createShare()` delegate to it, and it is passed into the ownership transfer above. A Core port with these methods would copy the Files interface method for method, which is not allowed. | B6. |
| `lib/Service/FileService.php` | `lib/Files/Service/File/FileAuditHandlerInterface.php` | `getAuditHandler(): FileAuditHandlerInterface` is a public method that `FileServiceInterface` declares. Its callers (`FilesController`, `FileMetadataFormHandler`, the bulk download in `ObjectsController`) call `logFileAction` and `logBulkDownload` on what it returns, so a narrower Core return type breaks them, and one with both methods copies the Files interface. | B6. |

What the row move does on 6655f596:

| Rows counted to Files | Gone | New against the order | Newly exposed Core files |
|---|---|---|---|
| Only `FileService.php` | 6 | 2: `Service/Deletion/DestructionCompanions` and `Service/File/ObjectFileReader` to `FileService` | 14 (`FileService`'s own handlers and bags in `lib/Service/File`, which stay Core) |
| B6: `lib/Service/File/*` minus A2, and `FileService.php` | 24 | 19, from Core's save, merge, share, deletion, anonymisation and registrar code (`SaveObject`, `FilePropertyHandler`, `MergeHandler`, `AccessLinkActs`, `ObjectShareReader`, `ObjectShareSurface`, `ServiceRegistrar`, `DestructionCompanions`, `PipelineSteps`, `SharerAccessSweepJob`, `PublishedDigestVerifyJob`, `DocumentStoreStatusCommand`) | 7 |

Counting `FileService` alone exposes its handlers, so it has to move with them. The handlers are packages U01
and U02. B6 waits for the Files design's B3 (Core folder and sharing callers through C1 and C2) and B4 (the
bulk download endpoint), and for the A1 csv rows of the digest job, the digest table and the document store
command. Then all six `FileService` references go in the B6 PR, with no new ones.
