# U07: references against the area order that remain

Work package U07 owned eight references (measured on main 3ec81519). Four are removed by the U07 pull requests, two are removed by open pull requests of earlier packages, and two are kept. Paths are under `lib/`.

## Removed by U07

| Source | Target | Move |
|---|---|---|
| `BackgroundJob/QueuedJobClassesInterface.php` (Core) | `BackgroundJob/TranslationProjectionJob.php` (Processes) | The handle moves to the Processes holder `ProcessesJobHandlesInterface`; the empty Core holder is removed (each area registers its own job handles). |
| `Db/SourceMapperInterface.php` (Core) | `Db/Source.php` (Integrations) | The contract returns `Kernel\Contracts\SourceInterface`, with a covariant template carrying `Source` for Integrations callers. |
| `Db/ApplicationMapperInterface.php` (Integrations) | `Db/Application.php` (Configuration) | The contract returns `Kernel\Contracts\ApplicationInterface`, with a covariant template carrying `Application` for Configuration callers. |
| `Db/MagicMapper/MagicSearchHandler.php` (Core) | `Search/Service/Search/PropertySearchProfile.php` (Search) | The handler reads the injected `Kernel\Contracts\PropertySearchProfileInterface`, which Search already binds in `SearchWiring`. |

## Removed by open pull requests of other packages (not duplicated here)

| Source | Target | Pull request |
|---|---|---|
| `Db/SchemaMapper/ExchangeAnnotationRefusals.php` (Core) | `Mcp/Service/Mcp/McpAnnotationValidators.php` (Integrations) | #10836 (P42): Integrations contributes the MCP check through `SchemaDeclarationChecksEvent` in its existing slot. Redoing it here would collide on the listener-order pins and the `ListenerRegistrar` move. |

A second copy of those rows and binding moves would conflict with it. |

If either pull request is closed without merging, its reference falls back to this package's list with the same fix.

## Kept

| Source | Target | Why no allowed move fits now | What lets it go later |
|---|---|---|---|
| `Controller/Support/GeoServices.php` (Core) | `Search/Service/Geo/GeoFeatureCollectionBuilderInterface.php` (Search) | `GeoServices` is the geo bag of `ObjectsController`. Its GeoJSON and WFS endpoints (`geoJson`, `wfs`) hand rows to the builder with Search's `FeatureShape` and `GetFeatureRequest`, which `ObjectsController` constructs itself (those are separate references of `ObjectsController`, owned by another package). A Core port for the builder would have to name the same Search value objects, so it only moves the reference; moving the value objects to Kernel by row would be a move only to hide it. The spatial-filter half of the bag already goes through the Core port `SpatialFilterInterface` (#10853). | Move `geoJson` and `wfs` (and probably `geoSearch` / `geocode`) into a Search controller with the same URLs and verbs in `appinfo/routes.php` (decision taken for `ObjectsController` endpoints of another area). Those endpoints build on the RBAC-scoped listing of `ObjectsController::index()`, so that first needs a Core port for "RBAC-scoped listing rows". Then `GeoServices` either moves with the endpoints (Search) or loses the builder. |
| `Db/Schema/ConfigurationValueRules.php` (Core) | `Service/Calendar/CalendarDateDeclarationCheck.php` (Processes) | The check refuses unusable calendar date declarations inside `Schema::setConfiguration()`: the entity constructs `ConfigurationValidator`, which builds `ConfigurationEntryRules` and `ConfigurationValueRules` with `new`. There is no container and no event dispatcher at that point, so neither a port nor an event can reach a Processes implementation. Moving the check to the schema-save collection (`SchemaDeclarationChecksEvent`) would change when it refuses: today `hydrate()` and imports refuse at set time, before any save. | The decision already taken: `Schema::setConfiguration()` validation moves to the Core write path after a golden test pins today's behaviour. Once configuration validation runs in a Core service, Processes contributes the calendar date check to it (a positioned contribution as in #10685, in the `calendarProvider` entry's place), and `ConfigurationValueRules` keeps only the required-field checks. |
