# U01: references kept, with the reason

Package U01 (wave 4) had 13 references against the area order, measured on main 3ec81519. Two are removed by #10950: `Service/Rbac/AuditRowWriter.php` and `Service/User/ApiTokenAuditRow.php` to `Db/AuditTrail.php`. The 11 below are kept.

Paths are relative to `lib/`. Areas: Kernel < Core < Notifications < Search < Compliance < Files < Integrations < Processes < Configuration < Platform.

## Core to Files: the file-storage handlers (4)

| Source | Target | Why no allowed move fits | What lets it go |
|---|---|---|---|
| `Service/File/ReadFileHandler.php` (Core) | `Service/FileHandlerSupportInterface.php` (Files) | The handler calls back into `FileService` through `setFileService(FileHandlerSupportInterface)`, for `extractFileNameFromPath()` and `getFilesForEntity()`. That is file-storage work calling file-storage work. A Core port with those methods would copy the Files interface method for method (ADR-119 Decision 13). Typing a narrower existing Core contract does not help: `getFilesForEntity()` is declared on the Files `FileFolderServiceInterface`, and `extractFileNameFromPath()` only on `FileHandlerSupportInterface`. | Files contract design (`contracts/files.md`), B6 PR 2: `Service/File/*` and `FileService` count to Files, wired by `FilesRegistrar`. Then this is Files to Files. |
| `Service/File/UpdateFileHandler.php` (Core) | `Service/FileHandlerSupportInterface.php` (Files) | Same callback (`getFile`, `checkOwnership`, `getFileTags`, `attachTagsToFile`, ...). Same reason. | B6 PR 2. |
| `Service/File/UpdateFileHandler.php` (Core) | `Files/Db/File.php` (Files) | `updateFileMetadata()` returns the written `Files\Db\File` entity, and `FileService` passes it on to its callers (54 fleet users of `FileService`). Narrowing the return type to a primitive or a Core contract changes a signature other apps read. #10883 and #10927 measured it the same way. | B6 PR 2 (A1): `Files\Db\File` is internal to Files once the handlers count to Files. |
| `Service/File/UpdateFileHandler.php` (Core) | `Files/Db/FileMapperInterface.php` (Files) | The metadata write goes through the Files mapper and returns the Files entity. Putting the metadata writes on the Core `ObjectFileRecordsInterface` would pull the Files entity into a Core port, which adds a reference against the order instead of removing one (#10883). | B6 PR 2. |

Rowing only these two handlers to Files is not an option: #10927 measured that moving the four handlers of this cluster alone removes 7 references, adds 8 (`DeleteFileHandler`, `DeleteFileSources`, `FileNodeHandlers` twice, `FilePublishingHandler`, `UpdateFileLocator`, `FileService` twice) and exposes 10 handler files. The cluster moves as a whole, after B1 to B5.

## Kernel to Core: `Db/Schema.php` (7)

Decision already taken (BRIEF.md, L2 decision 2): an entity method that constructs a Core class is deprecated, every openregister caller moves to the Core class, and the method keeps working until no app calls it. No static port registry. So each reference below disappears only when its method is removed, in a later breaking change. All these methods are also declared on the published Kernel contract `Kernel/Contracts/SchemaInterface.php`, so removal changes that contract too.

Moving a helper into Kernel by csv row does not fit any of them (L2 decision 1: only when its only users are Kernel classes and it holds no Core logic; ADR-119 Decision 13: never only to hide a reference):
- `DeclaredActions`, `VocabularyEntries`, `UniqueConstraintEvaluator` and `ConfigurationValidator` have Core users besides Schema (`AuthorizationBlockCheck`, `PermissionHandler`, `ConfigurationEntryRules`, `UpsertOnKeyHandler`, `WriteOnlyPathsDeclaration`, ...).
- `AuthorizationRulesValidator` needs the Core `PermissionCatalogueInterface`, and `PropertyAuthorization` the Core `ScopedPropertyDeclaration`: in Kernel each would trade its reference for another Kernel to Core one.
- `SchemaGrantEvaluator` names only Kernel value objects and only Schema uses it, but it is RBAC grant evaluation (Core's work), and it exists only for the deprecated duplicate `hasPermission()`. Moving it would hide the reference, not remove the dependency.
