## 3. Adoption proof
- [ ] 3.1 Migrate OR's own SettingsController canonical surface onto the generic service (kitchen-sink extras stay in their own controllers)
- [x] 3.2 Adopt HandlesApiExceptionsTrait in OR controllers (wave 1: the 20 highest-traffic)
  - Started: `MappingsController` (show, create, update, destroy) answers through `handleApiException()`; typed failures keep their status and message, anything else is a generic 500 with the detail in the server log.
  - `RegistersController` (show, create, destroy, schemas, the import soft delete) answers its generic failures through `handleApiException()` too: the public `show` no longer returns the exception message, and a constraint failure on delete is a 409. Its 400 answers (export, import, template) are unchanged. The other 18 controllers of wave 1 remain.
  - `SchemasController` (destroy, related, stats, indexes) answers its remaining generic failures through `handleApiException()`: an unknown schema on delete is now a 404 and a constraint failure a 409, while an untyped failure stays the generic 500. Its earlier typed catches (archival 403, attached-objects 409, the 404s) are unchanged. The other 17 controllers of wave 1 remain.
  - `WebhooksController` create, update, test and the log listing answer generic failures through `handleApiException()`: the exception message no longer reaches the response body, the log keeps the sent field names (never their values).
  - `OrganisationController` usage, isolationVerify and isolationMetrics answer their generic failures through `handleApiException()`: an unknown organisation on usage is a 404, anything untyped a generic 500. Its 400 answers (membership, create, update, lifecycle) are unchanged; its private 400 helper is renamed `badRequestResponse()` so it no longer shadows the trait's `errorResponse()`.
  - `RetentionController` (approve and reject a destruction list, place, release and bulk-place a legal hold) answers its generic failures through `handleApiException()`: an unknown object on a hold is a 404, anything untyped a generic 500 with the detail in the server log. Its 400 and 409 answers are unchanged.
  - `ArchivalController` write failures (approve and reject a destruction list, create and release a legal hold) share one helper: a typed failure answers through `handleApiException()` with its own status (an unknown object is a 404), anything else a 500 naming the action only, the cause in the server log.
  - `FormLinksController` (linked and available forms listings) answers its generic failures through `handleApiException()`: the exception message no longer reaches the response body.
  - `DeletedController` (list, statistics, top deleters, restore, permanent delete, the bulk restore and destroy, the destruction preview and record) answers its generic failures through `handleApiException()`. Its access bundle `DeletedAccess` gains an optional logger, so the detail of an untyped failure is logged rather than returned. The other 11 controllers of wave 1 remain; several of them (AuditTrail, Bulk, Mcp, Deck, CalendarEvents, ActivityLinks, ImportPreview) need a logger wired the same way first.
  - `TablesController` (sync one, sync all) and `TmloController` (MDTO export single and batch, the TMLO summary) answer through their failure helpers: a typed failure goes through `handleApiException()` with its own status (an unknown register on sync is a 404, an argument failure on the batch export a 400), an untyped one is a 500 naming the action, the exception message in the server log only. The schema card's sync toast falls back to the response's `error`.
  - `ConversationController` (list, create, and every action on one conversation: show, messages, update, delete, restore, permanent delete) and `RelationsController` (the relations of an object) answer generic failures through `handleApiException()`: the exception message no longer reaches the response body, a typed failure keeps its own status.
  - `SchemaImportController` (import, reimport) answers a persistence failure through its helper: a typed one via `handleApiException()` with its own status, anything else a 500 naming the action, the cause in the server log.
  - `McpController` (the public discovery catalog, a capability's detail, the grantable rights) answers its failures through `handleApiException()`: the public catalog no longer returns the exception message. Its services bundle `McpControllerServices` gains an optional logger, so an untyped failure's detail is logged.
  - `DeckController` (the cards of an object, the objects on a board) and `ActivityLinksController` (the activity of an object, the type and actor filter values) answer their generic failures through `handleApiException()`: the exception message no longer reaches the response body, a typed failure keeps its own status. Their services bundles gain an optional logger, so the detail of an untyped failure is logged.
  - `CalendarEventsController` (the events of an object, the calendars, the events of a calendar) answers its generic failures through `handleApiException()`: an unknown calendar stays a 404, a typed failure keeps its own status, anything else is a generic 500 with the detail in the server log. Its 400 answers on writes are unchanged; its services bundle gains an optional logger.
  - `ImportPreviewController` (build a preview, commit one) answers its untyped failures through `handleApiException()`: a typed failure keeps its own status, anything else is a generic 500 with the detail in the server log. Its 400 and 409 answers are unchanged; its services bundle gains an optional logger.
  - `BulkController` (bulk delete, bulk save, and the schema, objects and register table deletes) answers its generic failures through `handleApiException()`: the exception message no longer reaches the response body, the operation is named in the server log line instead, and a typed failure keeps its own status. The deliberate refusals (404, 403 archival, 409 frozen, 423 locked, 422 UUID conflict) are unchanged; its services bundle gains an optional logger.
  - `AuditTrailController` (export, clear all, the integrity status, the chain verification, the processing activities, the subject audit trail) answers its generic failures through `handleApiException()`: the exception message no longer reaches the response body, the operation is named in the server log line, a typed failure keeps its own status. Its 400 and 404 answers are unchanged; its services bundle gains an optional logger. This completes wave 1.
