  - Done (25 Nov, sandbox Nextcloud 34 + OpenRegister main on MariaDB 10.11 via `php -S`): `tests/newman/openregister-case-insensitive-ordering.postman_collection.json` (23 requests, 34 assertions, 0 failed) seeds `banaan`, `Appel`, `Cherry`, `aardbei`, `appel`, and asserts ascending, descending, a non-string property still numeric, and paging by one listing every record once in the same order. `tests/e2e/ci/case-insensitive-ordering.spec.ts` (1 passed) clicks the title header on the Tables page. It FOUND A DEFECT: the header stored its sort as `sortKey`/`sortOrder`, which the search store sent to the API as two unknown property filters, so clicking any column header EMPTIED the list. Fixed in `src/views/search/searchSort.js` (the sort goes out as `_order`, the header state is read back from it); the spec fails on main (`sortKey=title&sortOrder=asc` sent) and passes with the fix.
- [x] 1.5 MariaDB: if CI has no MariaDB job, run the Newman request once against a MariaDB instance and record the result in the PR body; say plainly if that run did not happen.

  - Done: the Newman collection above ran against MariaDB (Nextcloud installed with `--database mysql`, default `utf8mb4_general_ci`), 34/34 assertions. Observed: on that collation the raw-value tiebreak compares `Appel` and `appel` as equal, so the two keep `_id` order in BOTH directions (descending lists `Appel` before `appel`); the spec text asks for the raw value "in the same direction", which PostgreSQL's deterministic collation honours and MariaDB's case-insensitive one cannot. The collection therefore asserts the lower-cased order and that both spellings sit together, not the order inside the tie. No PostgreSQL run in this sandbox.
