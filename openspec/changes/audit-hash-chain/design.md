# Design: audit-hash-chain

## Context

Audit trails in OpenRegister track all changes to objects — who changed what, when, and the
before/after snapshots. These trails are immutable by design (no UPDATE/DELETE on audit
entries), but a determined attacker with database access could still modify stored entries.
Hash chaining detects any such tampering immediately: each entry's hash depends on the
previous entry's hash, so modifying any historical entry breaks the chain for all subsequent
entries. The verification endpoint lets auditors (or automated compliance systems) check the
chain's integrity without requiring cryptographic keys or signed timestamps.

## Goals

- Every audit trail entry MUST have a hash that chains to the previous entry.
- The first entry MUST use a well-known genesis hash to anchor the chain.
- Any tampering MUST be detectable via the verification endpoint.
- Concurrent writes MUST NOT produce broken chains (serialization requirement).
- Pre-migration entries (created before this change) MUST continue to work, skipped during
  verification.

## Non-Goals

- Cryptographic signing or certificate pinning.
- Distributed ledger or blockchain.
- Automatic alerts on detected tampering (compliance team decides action).
- UI visualization of the hash chain (backend-only in this change).
- Export of audit trails with attached proofs.

## Decisions

### D1. Hash algorithm: SHA-256

SHA-256 is industry-standard, well-vetted, and available in all modern PHP versions via
`hash('sha256', ...)`. MD5 rejected (cryptographically broken). SHA-1 rejected
(deprecated). **Chosen:** SHA-256.

### D2. Genesis hash constant

All chains must start somewhere. Using a database lookup for the "first entry" is fragile
(entry IDs may not be sequential; gaps can exist). **Chosen:** a well-known constant
`SHA-256("openregister-genesis-v1")` — published in the spec, easy to audit, and versioned
so future changes don't break legacy chains.

### D3. Canonical JSON for entry data

Hashing the JSON representation of the entry data makes the hash deterministic and
auditable. Different JSON encodings (key order, whitespace) MUST NOT produce different
hashes. **Chosen:** sorted keys + no whitespace (compact canonical form per RFC 8785 /
JCS). Exclude `hash` and `previousHash` from the computation (they depend on the content,
not vice versa).

### D4. Verification endpoint design

A dedicated endpoint is cleaner than embedding hash status in every audit-read response.
Range parameters (`from`, `to`) allow auditors to verify specific date ranges without
scanning the entire table. **Chosen:** `GET /api/audit-trails/verify[?from=ID&to=ID]` returning
`{valid: bool, entriesVerified: count, brokenAt?: ID, skippedNullHashes?: count}`.

### D5. Serialization strategy

If two `INSERT`s race, both may compute `previousHash` from the same "last entry," resulting
in two entries with identical `previousHash` values. This breaks the uniqueness of the chain.
**Chosen:** serialize writes via database transaction isolation (SERIALIZABLE or row-level
locking), enforced in the service layer. PHPUnit test covers concurrent writes.

### D6. Handling pre-migration entries

Backfilling hashes on millions of historical entries is expensive and risky (blocks the
migration). **Chosen:** leave existing entries with `hash = NULL`, `previousHash = NULL`;
verification endpoint skips them and returns a count in `skippedNullHashes`. Once a new
entry is written post-migration, the chain begins at that entry.

### D7. Index on hash column

Verification queries iterate all entries, but we may want to search by hash in the future
(e.g., "was this exact entry ever in the log?"). **Chosen:** add an index on `hash` for
future compatibility and query performance.

## Reuse Analysis

- **AuditTrailService** (from openregister/openspec) — existing service for writing audit
  entries. Will be extended to compute and persist hashes.
- **AuditTrailController** — existing controller for reading audit trails. Will be extended
  to add the verification endpoint.
- **Database transaction support** — Nextcloud framework's `IDBConnection` already handles
  transactions; no custom isolation logic needed.
- No custom cryptographic libraries — PHP's built-in `hash()` function used directly.

## Seed Data

Audit trails are generated by object mutations (create/update/delete). Test data is seeded
via mock objects in the `openregister_register.json` template, not manually. Hash chaining
itself requires no additional seed data; the service layer computes hashes automatically on
entry creation.

For testing purposes, 3 example audit entries (with hashes) are shown below to illustrate
the chain:

```json
{
  "id": 1,
  "userId": "admin",
  "action": "create",
  "timestamp": "2026-01-01T10:00:00Z",
  "objectId": "obj-1",
  "register": "cases",
  "schema": "Case",
  "data": {"title": "Case A", "status": "open"},
  "previousHash": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
  "hash": "abc123def456..."
}
```

Entry 2 (chained from entry 1):
```json
{
  "id": 2,
  "userId": "staff",
  "action": "update",
  "timestamp": "2026-01-01T10:30:00Z",
  "objectId": "obj-1",
  "register": "cases",
  "schema": "Case",
  "data": {"title": "Case A", "status": "in_progress"},
  "previousHash": "abc123def456...",
  "hash": "def456ghi789..."
}
```

Entry 3 (chained from entry 2):
```json
{
  "id": 3,
  "userId": "admin",
  "action": "delete",
  "timestamp": "2026-01-01T11:00:00Z",
  "objectId": "obj-1",
  "register": "cases",
  "schema": "Case",
  "data": {"reason": "merged with Case B"},
  "previousHash": "def456ghi789...",
  "hash": "ghi789jkl012..."
}
```

If an attacker modifies entry 1's `data`, its `hash` no longer matches the recomputed value,
and entry 2's `previousHash` points to the stale entry 1 hash — verification immediately
detects the break.
