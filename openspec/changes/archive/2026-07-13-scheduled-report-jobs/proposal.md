# Scheduled Report Jobs

## Problem
Every Conduction app on the fleet — controllers, management, back-office teams — routinely needs a *recurring* export ("send me the weekly open-cases list every Monday morning", "drop a daily CSV of new registrations into my Files"). Today OpenRegister only supports **on-demand** export: a user must remember to click "export" every time. No layer in the fleet offers scheduled/recurring report delivery.

OpenRegister already has everything this needs as building blocks: `ExportService` (CSV/Excel/JSON and, as of PR #371, PDF, all RBAC- and multi-tenancy-aware) and 40+ background-job classes proving the `TimedJob`/`QueuedJob` patterns. Per ADR-Leaf-First, this change composes those existing leaves into scheduled report delivery available to every app at once, rather than each app reinventing it.

This also closes a real gap the fleet's own specs already flagged: `openspec/changes/rapportage-bi-export/` (status: `proposed`, unimplemented) reserves a `ScheduledReportJob` (extending `TimedJob`) and describes exactly this shape in its "The system MUST support scheduled report generation" requirement — including its own "Schedule a daily CSV export for data warehouse" scenario (`ExportService::exportToCsv()`, Files delivery, dated filename) and "Schedule a weekly status report" scenario (Files + `INotifier` notification to the owner). That requirement is still listed under `rapportage-bi-export`'s "Not implemented" section today. This change implements it, using the reserved class name and satisfying those two scenarios directly.

It is **not** the same as the already-shipped `ReportRenderJob` (`lib/BackgroundJob/ReportRenderJob.php`), which is a different, narrower mechanism: a daily job that renders the operator-imported BI **`reports` register**'s dashboard objects (branded/templated aggregation reports) via `ReportRenderService`, Files-only, no notifications yet. This change is the generic counterpart: schedule an `ExportService` export of **any** register/schema + filter combination — the same shape every export endpoint already accepts — available without needing the BI reporting bundle installed at all. The two jobs coexist; `rapportage-bi-export`'s remaining scope (report templates, branding, aggregation sections, OData, retention, n8n email delivery) stays open and unaffected.

## Proposed Solution
1. **`ScheduledReport`** entity + `ScheduledReportMapper` (plain `QBMapper`-backed infrastructure row, following the `PushSubscription`/`PushSubscriptionMapper` convention — not an OR object/register, per ADR-001): owner uid, register/schema reference, opaque filter JSON (same shape the export endpoints accept), format (`csv|excel|pdf`, validated against `ExportService`'s supported set), a simple schedule (`daily|weekly|monthly` + hour, no cron expressions per scope), delivery folder, enabled flag, `lastRunAt`/`lastStatus`/`lastError`.
2. **`ScheduledReportService`** — validation, ownership-scoped CRUD, catch-up-safe due-computation, and `runOne()`: impersonates the report owner (`IUserSession::setUser()` + try/finally restore, the established `HandoffService` pattern) so `ExportService` applies the owner's own RBAC/multi-tenancy scope, calls the matching `ExportService::exportTo*()` method, writes the result into the owner's Nextcloud Files (`IRootFolder::getUserFolder()`, default folder `Reports/`, same path-traversal hardening as `ReportRenderJob::writeToFiles()`), and sends an `INotifier` notification linking to the file. Catches `ExportTooLargeException` (and any other failure) per-report: marks `lastStatus = failed` with a reason, notifies the owner, and does **not** retry-loop.
3. **`ScheduledReportJob`** (hourly `TimedJob`) — the reserved class name from `rapportage-bi-export`. Loads enabled reports, checks each for due-ness (elapsed-period-since-`lastRunAt`, catch-up-safe), and calls `ScheduledReportService::runOne()` per report inside its own try/catch so one failing report never aborts the rest.
4. **`ScheduledReportRunNowJob`** (fire-once `QueuedJob`, mirroring `WebhookDeliveryJob`'s dispatch-via-`IJobList::add()` pattern) — the target of the REST `run-now` action, so an immediate export never runs inline inside the HTTP request.
5. **`ScheduledReportsController`** — REST CRUD (`index` own rows, admin sees all; `show`/`create`/`update`/`destroy` owner-or-admin-gated; `run-now` queues `ScheduledReportRunNowJob`), routes in `appinfo/routes.php` following the `webhooks#*`/`notificationSubscriptions#*` conventions.
6. Email delivery is explicitly **out of scope** for this change (SMTP is not managed by OpenRegister — see `rapportage-bi-export`'s n8n-workflow email scenario for the planned mechanism); this change delivers via Files + notification only, and documents email as a future extension.

## Alternatives Considered
- **Model scheduled reports as OR objects/register rows** (like the BI `reports` register `ReportRenderJob` reads): rejected — a scheduled-export config is infrastructure state owned by exactly one user with no business/relation/audit value, the same reasoning that put `PushSubscription`/`Webhook` in `lib/Db` rather than the object store (ADR-001). It would also force every app to install the BI reporting bundle just to get a recurring CSV export, defeating the "available to every app at once" goal.
- **Cron-expression scheduling**: rejected per explicit task scope — `daily|weekly|monthly` + hour covers the vast majority of real recurring-report needs (weekly Monday morning case lists, daily data-warehouse drops) with far simpler validation and due-computation than a full cron parser.
- **Run the TimedJob's exact `run()` body for run-now too** (no separate `QueuedJob`): rejected — running an export inline inside the HTTP request thread blocks the response on `ExportService` (which can take seconds for large registers, longer still for PDF rendering), exactly the latency problem `WebhookService::dispatchEvent()` already solved by moving delivery to `IJobList::add()` + a dedicated job class.

See `design.md` for the due-logic semantics, owner-impersonation mechanics, and the full reconciliation with `rapportage-bi-export`/`ReportRenderJob`.
