# Migration Mapping Packs

## Problem
Migrating from an old zaaksysteem routinely costs a municipality 25–50% of the total procurement budget, and that cost skews vendor decisions toward whatever migrates cheapest — excellent migration tooling wins deals. OpenRegister already has a capable `ImportService` (CSV/JSON/Excel with per-row error reporting and a rollback contract), but every migration starts from zero: the operator must hand-map every legacy export column onto the target schema, for every file, every time. There is no way to capture a source-format→schema mapping once, reuse it across imports, share it between instances, or — critically for migration *quoting* — see exactly what an import would do before committing to it.

## Proposed Solution
1. **Declarative migration packs** — a small JSON document (`id`, `name`, `sourceFormat: csv|json|excel`, semver `version`, `fieldMappings` with per-field `transform`s, `defaults`, `skipRows`, `idStrategy`) describing how one legacy export shape maps onto schema properties. One testable `PackDefinitionValidator` (structure + allow-lists) and one `MappingEngine` (applies a pack to one parsed row; format-agnostic — flat column names for CSV/Excel, JSON-Pointer paths for JSON).
2. **Literal-leak guard** (fleet lesson: an unresolved template/transform reference must never pass through as a literal): a `lookup`/`bool-map` whose source value has no map entry and no configured `default` ERRORS the row — the raw unmapped value never reaches the saved object.
3. **Storage + management** — packs stored as infrastructure DB rows (`MigrationPack` entity + `MigrationPackMapper` over `openregister_migration_packs`, following the `ScheduledReport` convention, NOT OR objects — see design.md), with REST CRUD (reads for any authenticated user, mutations admin-gated) plus import/export of pack definitions as standalone JSON files so packs can be shared between instances.
4. **Execution through the existing import flow** — `registers#import` accepts an optional `packId`; `ImportService` runs each row through the `MappingEngine` before its normal validate/save pipeline. The single write path (`ObjectService::saveObjects()`/`saveObject()`) is preserved; mapping errors are reported in the existing per-row error format, labeled with source column + transform.
5. **Dry-run mode** — `dryRun=1` maps + validates every row and saves NOTHING, returning the per-row valid/invalid report. This is the migration-quoting feature: an operator can price a migration by running the actual export against the actual pack with zero side effects.
6. **One built-in reference pack** — `zgw-zaken-json`, mapping the ZGW Zaken API export shape (a Dutch-municipal standard we can verify) onto a generic case-like target, explicitly marked as a template. Proprietary vendor formats (Decos, Centric) are deliberately NOT fabricated — documented as pack-authoring candidates in design.md instead.

## Alternatives Considered
- **Store packs as OR objects in a register**: rejected — packs are admin-managed infrastructure config with no business meaning, no relation/audit value, and a hard availability requirement during import; the `ScheduledReport`/`PushSubscription` `lib/Db` convention fits exactly (ADR-001).
- **Reuse the webhook-payload-mapping / zgw-api-mapping DSLs**: examined; both are direction-specific (outbound webhook payload shaping, ZGW API resource mapping) and neither models per-row imports with row-scoped error reporting, skip rows, or id strategies. A third vocabulary is justified because the pack document is a user-facing, shareable artifact — but the `fieldMappings`/`transform` naming deliberately stays close to those precedents.
- **Wire packs into Excel multi-sheet import too**: deferred — multi-sheet mode fans out one file across many schemas while a pack targets exactly one schema shape. `packId` on an Excel import returns a clear 400 rather than being silently ignored (no orphaned/no-op parameters); single-sheet Excel migration exports can be saved as CSV. Documented follow-up.

See design.md for the storage decision, the reference-pack rationale, and the dry-run side-effect-freedom analysis.
