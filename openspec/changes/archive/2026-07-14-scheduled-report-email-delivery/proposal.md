# Scheduled Report Email Delivery

## Problem
`scheduled-report-jobs` (PR #387, merged 2026-07-13) shipped recurring scheduled exports with Files-only delivery, and explicitly documented email as future work: its `design.md` "Future extensions (explicitly out of scope here)" section states *"Email delivery — `rapportage-bi-export`'s n8n-workflow email scenario remains the planned mechanism; this change's `deliveryFolder`/notification-link approach covers the Files + in-app-notification half of that requirement"*, and its `proposal.md` scope list item 6 says the same. That planned n8n mechanism (`rapportage-bi-export`, status `proposed`, unimplemented) is a separate, much larger workflow-engine capability. Meanwhile the concrete, immediate need is simpler: let a scheduled report land in someone's **inbox**, not only their Nextcloud Files — the exact "weekly status report to the team" and "daily CSV export to a distribution list" use cases the feature already targets, without waiting on the n8n integration.

## Proposed Solution
1. **`ScheduledReport` gains two fields**: `deliveryMode` (`files` default | `email` | `both`) and `recipients` (opaque JSON array of email addresses, capped at 20, each validated as a syntactically correct address at create/update time — same "reject at config time, not at run time" discipline `scheduled-report-jobs` already applies to `format`/`scheduleType`). An empty/absent `recipients` list means "the owner's own Nextcloud email address, resolved at run time" (`IUserManager`/`IUser::getEMailAddress()`) — no separate distribution-list management UI needed for the common single-recipient case. A new migration (`Version1Date20260714000000`) adds the columns; the shipped `Version1Date20260713000000` migration is not touched.
2. **`ScheduledReportService::runOne()`** composes a second, independent delivery leg via `OCP\Mail\IMailer` (this app's first use of `IMailer`'s email-template/attachment surface — `FlowActionService`/`AnnotationNotificationDispatcher` already use its plain-message path for other features) when `deliveryMode` includes `email`: an `IMailer::createEMailTemplate()` email whose heading is the report name and body states register/schema/schedule/row-count, with the export file attached when it's under a 10MB cap. Over that cap, the attachment is omitted and the export is (if not already) delivered to Files instead, with a link in the email body — the data is never silently dropped. The Files leg (`deliveryMode` `files`/`both`) is unchanged.
3. **Isolated failure semantics**: a failure in the email leg does not undo or fail the Files leg. When `deliveryMode` is `both` and Files succeeds but email fails, `lastStatus` is set to a new, distinct value `email_failed` (not `failed`) carrying the reason in `lastError` — the export *was* delivered, just not by every requested channel. When `deliveryMode` is `email` only and the email leg fails outright (e.g. no resolvable recipient), nothing was delivered and the run is `failed`, matching the existing all-or-nothing semantics for a single delivery channel. Per-report isolation in `ScheduledReportJob`'s batch loop is unaffected.
4. **Controller/API**: `ScheduledReportsController::create()`/`update()` already forward the full request payload to the service, which now validates `deliveryMode`/`recipients` alongside the existing fields — no controller code change needed for accept/validate; `jsonSerialize()` (and therefore `index`/`show`) now includes both fields.
5. **Notifier**: the existing `scheduled_report_delivered` subject is reused for every mode (parameterized with `mode` and an optional `emailFailureReason`) rather than adding a new subject — `scheduled_report_failed` is likewise reused unchanged for the `failed` case.

## Alternatives Considered
- **Wait for the `rapportage-bi-export` n8n-workflow email mechanism**: rejected — that's a materially larger, unimplemented workflow-engine capability; this change delivers the concrete "email me the report" need now using the same `IMailer` pattern already established elsewhere in the app, without blocking on or conflicting with the eventual n8n integration (which can still be built as a richer alternative delivery channel later).
- **A new `scheduled_report_email_failed` notification subject**: rejected in favour of parameterizing the existing `scheduled_report_delivered` subject — the situation ("delivered, but with a caveat") is a variant of "delivered", not a new event type, and Nextcloud's `INotifier` subjects are cheap to parameterize but each new one adds a permanent case to `prepare()`'s switch and every consumer's subject-handling.
- **Hard-fail the whole run when email fails under `deliveryMode: both`**: rejected — Files delivery already succeeded; reporting the run as a hard `failed` would be misleading (the export DID reach the owner, just not by every channel) and could mask a real, actionable Files-side problem behind a spurious email transient (SMTP hiccups are common and shouldn't erase a successful delivery).

See `design.md` for the recipient-resolution/attachment-cap mechanics and the full `lastStatus` outcome table.
