# ADR-012: Functional components defined over the Nextcloud layout, with published contracts in the Kernel

**Status**: accepted (2026-11-09). Superseded in part by ADR-014: the SIG component definition. The published-contracts guidance stays as internal guidance.

**Date**: 2026-11-09

## Context

OpenRegister keeps the Nextcloud app layout: `lib/Controller`, `lib/Service`, `lib/Db`, `lib/Listener`,
`lib/BackgroundJob`, `lib/Command`, `lib/Repair`, `lib/Event`, `lib/Exception`, plus the feature directories
`lib/Files`, `lib/Search`, `lib/Notifications`, `lib/Mcp`, `lib/AppHost` and the shared `lib/Kernel`,
`lib/Contract`, `lib/Support`. The repository owner decided on 2026-11-09 that this layout stays.

Sigrid's automatic component detection, and `sigrid.yaml` as it stands (`component_base_dirs: ["lib", ""]`),
make every directory under `lib/` a component. Those are technical layers, so every call from a controller to
a service or from a service to a mapper is a cross-component call. Measured on main `e39b44f0`: 40,865 of
397,976 LOC exposed (10.27%, independence rating 2.63), violation degree 0.0598 (entanglement 3.91). The
layer view has a floor near 17,500 exposed LOC (rating about 3.9), because the Db layer exposes its entities
and mapper interfaces to every service, however many interfaces are added.

`ARCHITECTURE.md` describes the system as functional components ("a controller, its service and its mapper
for one capability sit in the same component") and states that every component depends on the data model.
Sigrid's scope configuration supports that description without moving files: a `components:` list where
each component has a `name` and regular-expression `include` and `exclude` patterns on the full path. Sigrid
documents this option as flexible and maintenance intensive, for project-specific component structures and
for technologies whose structure is not in SIG's knowledge base. A Nextcloud app is such a case.

Measured with our estimate tool extended to read that block (`tool-pattern-components.patch`): under the
functional definition, before any code change, 142,241 LOC are exposed (35.74%) and the violation degree is
0.1963. The interfaces built in earlier rounds sit on the layer boundaries; functional components call each
other's concrete classes directly (943 classes, 111,888 LOC). The definition therefore has to land together
with the contracts that make the components independent.

Other Conduction apps reference 351 OpenRegister class names in production code; 31 files in other apps
write through `SchemaMapper`, `RegisterMapper`, `ConfigurationMapper` and `OrganisationMapper` directly. The
alias layer (`lib/AppInfo/ClassAliasMap.php`, `appinfo/class-aliases.json`) exists and is tested.

## Decision

OpenRegister's components are functional and are defined in `sigrid.yaml` by file pattern over the Nextcloud
layout. Components talk to each other only through contracts in `lib/Kernel`. The published surface has a
budget. No file leaves its layer directory for this decision.

### Rule 1: the component definition

`sigrid.yaml` carries a `components:` block with ten components. The block is generated by
`scripts/component-patterns.py` from `scripts/component-map.csv` (the approved class map, one row per file
with its component) and is never edited by hand. `tests/Unit/Architecture/ComponentDefinitionTest.php`
asserts that every file under `lib/` matches exactly one component and that `scripts/component-map.csv` names
every file; a PR that adds a class to a flat layer directory adds its row.

| component | what it holds (over `lib/Controller`, `lib/Service`, `lib/Db`, `lib/Listener`, `lib/BackgroundJob`, `lib/Command`, `lib/Repair`, `lib/Event`, `lib/Exception` and the feature directories) |
|---|---|
| Kernel | `lib/Kernel`, `lib/Contract`, `lib/Dto`, `lib/Support`, `lib/Formats`, `lib/Lifecycle`; `Db/ObjectEntity`, `Db/Schema`, `Db/Register`, `SchemaMapperInterface`, `RegisterMapperInterface`; events and exceptions referenced by more than one component |
| Core | objects, schemas, registers, relations, merging, history, RBAC, organisations, credentials, sharing, delegation, the Magic mapper, object sources, vocabularies, views |
| Processes | flows, BPMN and DMN, rules, calculations, tasks, cases, forms, decisions, lifecycle transitions, object actions, bulk actions, Workflow Engine operations |
| Configuration | configuration packages and deployment, import and export, example sets, shipped baselines, migration packs, settings services, API versioning, repair steps |
| Compliance | archival, e-Depot, retention, deletion, GDPR, consent, audit trail, anonymisation, quality |
| Integrations | `lib/Mcp`, `lib/AppHost`, integration registry, GraphQL and API clients, calendar, contacts, DAV, federation, Context Chat, Twig, webhooks, outbound |
| Files | `lib/Files`, `lib/Service/File` |
| Search | `lib/Search`, `lib/Service/Aggregation`, `Service/GraphQL`, `Service/Search`, `Service/Vectorization`, `Service/View`, search trail |
| Notifications | `lib/Notifications`, `lib/Notification`, `lib/Push`, `lib/Activity`, parties, interaction |
| Platform | `lib/AppInfo`, `lib/Middleware`, `lib/Capabilities`, `lib/Dashboard`, `lib/Reference`, `lib/Sections`, `lib/Settings`, operations console |

Pattern form: a whole directory where it belongs to one component (`".*/lib/Service/Flow/[^/]*"`); one
alternation of class names per component in a flat layer directory
(`".*/lib/Controller/(FlowController|TasksController|...)[.]php"`). Kernel is listed first. The generated block
for main `e39b44f0` is `components-v2-final.yaml` in the design directory: 335 patterns, no file unmatched.

`component_base_dirs` is removed when the block goes in; Sigrid uses one or the other. The block goes into
`sigrid.yaml` when the contract lanes of Rule 2 have landed; until then it is kept
as `sigrid.components.yaml` so the tests and the gate enforce it, and the directory-based view is what Sigrid
rates.

### Rule 2: the published surface lives in the Kernel

A class in one component references a class in another component only when the referenced class belongs to
the Kernel component. Everything a component offers to another is an interface, a DTO or a value type in
`lib/Kernel/Contracts`, and the component binds the implementation in its own registrar.

- Interfaces that exist today in `lib/Service`, `lib/Search`, `lib/Files`, `lib/Notifications`, `lib/Mcp`,
  `lib/AppHost`, `lib/Listener`, `lib/BackgroundJob`, `lib/Repair` and `lib/Twig` and are referenced from
  another component move to `lib/Kernel/Contracts`. The old name stays valid through a lazy class alias until
  the last reference is updated.
- A concrete class another component uses gets a thin Kernel interface declaring only the operations that
  component invokes, grouped by capability (`ObjectsInterface`, `SchemasInterface`, `AccessInterface`,
  `FlowsInterface`, `TasksInterface`, `ConfigurationInterface`, `ArchivalInterface`, `FilesInterface`,
  `SearchInterface`, `NotificationsInterface`, ...), not one interface per class. The class stays where it is.
- Entities do not cross a component boundary, with the three Kernel entities `ObjectEntity`, `Schema` and
  `Register` as the exception. Another component receives an id, an array or a Kernel DTO; where it reads an
  entity today (488 getter calls measured), the owner's contract returns the value or a Kernel read
  interface stands in for the entity.
- Mappers are reached from another component only through their `*MapperInterface`, which lives in the
  Kernel.
- Small value classes passed between components become Kernel DTOs (`lib/Kernel/Contracts/Dto`), with an
  alias for the old name.
- Events stay in `lib/Event` and exceptions in `lib/Exception`; an event or exception referenced by one
  component belongs to that component by pattern, one referenced by several is Kernel. Events and exceptions
  name Kernel types only.

### Rule 3: the surface budget

The code that crosses component boundaries, measured as the exposed LOC of the SIG estimate tool under the
components block, is at most 11,000 lines for the whole application (the 4.5 line is 10,944), and the
violation degree is 0. The gate of ADR-013 reports both numbers on every PR and fails a PR that raises either
above the recorded value. The budget is lowered in steps as stage 3 lands; the target is 8,000. The Kernel
component is expected to hold about 8,000 LOC of contracts, DTOs, core entities, shared events and exceptions;
`ARCHITECTURE.md` says so instead of calling the Kernel small.

### Rule 4: names other apps use keep working

- Frozen in place and name: `lib/Db/ObjectEntity.php`, `Schema.php`, `Register.php`, `SchemaMapper.php`,
  `RegisterMapper.php`, `lib/Service/ObjectService.php`, every class in `lib/Event` and `lib/Exception`,
  `lib/Contract`, the Workflow Engine operations. Nothing in this decision moves them.
- An interface or value class that moves into `lib/Kernel` or `lib/Support` gets an entry in
  `appinfo/class-aliases.json` (lazy alias and container service alias; eager when another app names it in
  `instanceof`, `catch` or a type declaration). Ten such interfaces are referenced by other apps today.
- Other apps do not change on the day of a move. `cross-app-usage.txt` in the design directory is the
  inventory.

### Rule 5: controllers stay in lib/Controller

Controllers keep their place and their routing. A controller belongs to its capability's component by
pattern. A controller calls services through the Kernel contract of another component and directly inside its
own component.

## Consequences

Positive:

- The directories stay what Nextcloud developers expect, and the component view says what
  `ARCHITECTURE.md` says. The map between the two is one generated block and one test.
- Entanglement becomes a star: every component depends on the Kernel and on nothing else, so the violation
  degree is zero by construction and the ADR-013 test keeps it there. Rating 5.0 with full margin.
- Independence can reach 4.5 and, with the surface shrunk, about 4.75 (8,000 exposed LOC); the layer view
  could not pass 3.9.
- No class moves between layer directories, so no routing, job or repair-step mechanics are touched; only
  interfaces and value classes move, and only into `lib/Kernel` and `lib/Support`.

Negative and costs:

- Switching the definition before the contracts exist shows independence about 1 star and entanglement
  about 2 in Sigrid. Decided 2026-11-09: the switch waits for the contract stage; until then the block lives in `sigrid.components.yaml` and the tests read it there.
- 335 patterns to maintain. The generator and the definition test carry that; a class added to a flat layer
  directory without a row in `scripts/component-map.csv` fails the build.
- Sigrid cannot detect sub-components under this option; the Code Breakdown view shows ten components with
  no inner structure.
- The Kernel grows to about 8,000 LOC; about 780 interface files change namespace, with aliases.
- Independence 5.0 (5,472 exposed LOC) is not reachable without moving code: the Kernel floor is about
  5,200 LOC before the first contract line, and the 2,240 cross-component operations need at least 1,500
  lines. 4.75 is the credible end state, 4.9 the stretch.
- Measurement is regex based in our tool and pattern matching may differ by a few files in Sigrid.

## Alternatives considered

- **Move files into functional directories (v1 of this ADR).** Projected independence 5.09 with moves of
  about 5,000 files and 13,900 fleet references through aliases. Rejected by the repository owner on 2026-11-09: the Nextcloud
  layout stays.
- **Stay with the directory-based components and add interfaces.** Ceiling 4.4% exposed, rating about 3.9.
  Rejected: it cannot reach the goal.
- **Define components with the single-caller rule applied.** Measured better (27% before contracts), but
  needs 4,137 patterns because it scatters files across directories. Rejected: unmaintainable and not
  readable as an architecture.
- **Thirteen functional components as in the approved map.** Objects, Schemas and Access exchange 786
  operations; as one Core those are internal. Rejected as the component list; the map stays the seed.
- **One interface per class.** The most expensive published surface; it mirrors the implementation.
  Rejected in favour of one thin interface per capability.
