## What this is

`quality / Integration Tests (Newman)` has been red on `development` since the round-2 merge, on one assertion: `17b. Unlock Object (Lifecycle)`. The previous lane called it a real signal rather than a harness fault and left it for a live check. It is a real signal, and this is what it was pointing at.

## What the collection was doing

Step 17 locks the object, 17a updates it as the lock holder, 17b posts to `/unlock` and expected 200. The unlock answers 404 with `error: not-locked`, because by then the object carries no lock. The owner's PUT at 17a is the only thing in between.

## Whether the lock should survive a PUT by its owner

It should not, and that is not an accident of this merge. A save is a check-in. `ObjectsController` has released the writer's own lock after a successful write since openregister#195, and `run-scoped-object-locking` ratified it: the requirement "a lock refuses a write and names its holder" carries the scenario "a successful write releases only the writer's own lock". A lock held by anybody else, a flow run included, survives the write, and that asymmetry is deliberate: a run's lock is meant to outlive every write the run makes.

What changed with the merge is only the report. `unlock()` used to answer 200 whether or not there had been a lock, so the release of a lock that was already gone was indistinguishable from a real one. It now answers 404 naming the fact. The collection was written against the old silence.

## The defect that was hiding behind it

The release goes to the database through `unlockObject()`, which re-reads the row. The entity the request is about to serialise keeps the lock payload it was loaded with, so the 200 body of a successful write reported a lock that the very same request had just released. A client that trusts the body it was handed, such as `@conduction/nextcloud-vue`'s `useObjectLock`, goes on believing it holds a lock until its release answers 404. That is the answer a second editor cannot act on, and it is fixed here.

## The change

- The three copies of the post-save release, on `update`, `patch` and `postPatch`, become one `releaseOwnLockAfterWrite()`. It clears the lock on the in-memory entity when the release happened, leaves it in place when the release threw, and never touches a lock held by somebody else. Nothing extra is persisted: the row is already unlocked and the entity is discarded after serialisation.
- `ObjectsControllerWriteReleasesOwnLockTest`, four tests. The release case, the other-holder control, the unlocked control, and the failed-release case where the body must keep reporting the lock because the row still carries it.
- Newman 17a now asserts that the write's own body no longer claims the lock. 17b asserts the 404 and its `not-locked` body. Two new steps, 17b1 and 17b2, re-take the lock and release it, so the collection still covers the 200 release path instead of only the no-op.

## Verification

- `phpunit --testsuite="Unit Tests" --filter ObjectsController`: 381 tests, 0 failures, 4 skipped.
- Mutation: removing `setLocked(null)` reddens `testTheBodyOfAWriteStopsClaimingTheLockThatWriteReleased` on its own assertion, `The write released the caller own lock, so the response must not report one. Failed asserting that Array &0 ['user' => 'alice', ...] is null`, and nothing else.
- The first draft of that test read `$body['locked']` and passed while measuring nothing: the lock lives under `@self`, and a top-level `locked` key is absent whatever happens. The test now reads `$body['@self']['locked']` and the note is in the file so the next reader does not repeat it.
- `phpcs`, `phpstan` and `psalm` on `lib/Controller/ObjectsController.php`: clean.
- The Newman collection is not runnable in this lane, which has no instance of its own. CI is the arbiter for that leg.
